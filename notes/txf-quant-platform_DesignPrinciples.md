# txf-quant-platform 核心防禦性設計準則 (Design Principles)

> **目標**：從寫下第一行程式碼開始，徹底阻絕「技術債」、「模組耦合」與「架構混亂」，確保系統在未來新增 100 個特徵或 50 支策略時，依然保持極致的輕巧與穩定。

為了向您保證這個專案絕對不會重蹈覆轍，我們將在開發前確立以下 **五大鐵律 (Iron Rules)**，這將是我們未來撰寫每一行程式碼的合約：

---

### 鐵律 1：嚴格的介面隔離 (Strict Interface Segregation)
**痛點**：以前只要改了永豐 API 的接收方式，看盤 UI 就會跟著壞掉。
**解法**：策略 (`Strategy`) **絕對禁止**直接載入 Kafka 或永豐 Shioaji 的套件！策略只能認識 `FeedBase` (拿資料) 與 `BrokerBase` (下單)。
- **結果**：未來就算我們把券商從永豐換成群益，或者把資料源從 Kafka 換成 Redis，您的策略程式碼 **一行都不用改**。

### 鐵律 2：單向資料流與不可變性 (Unidirectional Data Flow)
**痛點**：模組互相改寫資料，最後不知道 Bug 是誰造成的。
**解法**：資料流永遠只能是：`Feed -> Data Engine -> Strategy -> Broker`。
- `Data Engine` 算出來的指標與 K 棒，對策略來說是 **唯讀 (Read-Only)** 的。
- 策略不能去修改歷史 K 棒的數值，只能根據數值產生 `Signal (訊號)`。這能 100% 保證回測與實盤的資料對稱性。

### 鐵律 3：狀態機防禦 (State Machine Guard)
**痛點**：實盤下單時，常常發生「程式以為已經平倉了，但其實單子還掛在市場上」，導致重複下單或留倉爆倉。
**解法**：導入嚴格的「訂單狀態機 (Order State Machine)」。
- 所有訂單的狀態 (`Pending`, `Filled`, `Canceled`, `Rejected`) 都統一由 `Execution` 模組掌管。策略端只能「請求下單」，不能自己宣告「我已經買到了」。

### 鐵律 4：設定檔與邏輯絕對剝離 (No Hardcoding)
**痛點**：為了換一個顏色、改一個週期、或是換一個商品，要在茫茫程式海裡尋找 `TXF` 字眼。
**解法**：嚴格實施配置分離。所有商品代碼、K棒週期、Kafka Topic、甚至是神經網路的 Hyperparameters，全部集中存放在 `config/` 目錄下的 YAML 或是專屬設定檔中。邏輯模組內做到「零硬編碼 (Zero Hardcoding)」。

### 鐵律 5：測試即文件 (Test-Driven Mindset)
**痛點**：修改了一個計算部位損益的公式，結果導致另一個策略的停損機制失效。
**解法**：對於核心數學邏輯（例如：未平倉損益計算、保證金維持率、手續費計算），我們將建立獨立的單元測試 (Unit Tests)。確保每一次架構升級，都能在 1 秒內自動驗證這些攸關金錢的算式沒有被破壞。

這套「防禦性編程 (Defensive Programming)」是頂級軟體工程的核心。當我們用這種心態來蓋房子，這棟大樓即使蓋到 100 層也不會歪斜。
